# SOC Report Review Tool: backend

Internal tool for third-party risk analysts. It stores vendors and their SOC reports year by
year, reads each new report, compares it with the prior report for the same vendor, system and
report type, and fills an Excel template with what changed. The analyst reviews every change
and makes every decision. Runs entirely on AWS; Claude is called through Amazon Bedrock.

The React SPA is in a separate repo, FrontendSO (D-27). This repo holds the Python code, all
CloudFormation templates and the shared docs.

## Rules with no exceptions

1. **The analyst always makes the decision.** The tool never approves, rejects or scores a
   vendor. Claude's impact tag is "suggested"; the analyst sets the final value (D-08).
2. **Synthetic PDFs only.** Never commit, upload or paste real SOC reports, text copied from
   them, or real vendor names and findings. Fixtures are generated by
   `tests/fixtures/generate.py`. Real reports wait for InfoSec and Legal (O-4).
3. **Scope is SOC 1 and SOC 2, Type I and Type II** (D-25). Bridge letters are open (O-10).
4. **Compare like with like:** same vendor, same system, same report type only (D-24).
5. **Comparison is computed in code** (D-09). Claude extracts and explains; it never compares.
6. **Every extracted item carries `page` and a verbatim `excerpt`**, checked in code against
   the Textract text of that page (D-10).
7. **Check current docs before using a model ID, limit, quota or price.** Do not rely on
   memory or values in this repo. Mark anything unverified in a comment.
8. **Every AWS resource comes from a CloudFormation template** (D-16). Never create or change
   resources from the console or ad-hoc CLI calls. A human approves every change set.
9. **No secrets in code or config.** IAM roles; Secrets Manager if unavoidable.
10. **Everything stays on AWS** (D-01). No new service without a new entry in `decisions.md`.

## How we work (one task = one branch = one PR)

1. `/clear`, then branch `t-xx-short-name` from `main`.
2. Plan mode: `/spec-task T-xx` writes `docs/specs/T-xx-*.md`. The human approves it.
3. Implement in a fresh session from the spec: tests first, then code, then `make check`.
4. Show evidence: test output; eval scores for any prompt or model change; the change set
   for any template change.
5. Review: run the `spec-reviewer` agent, then `/code-review` and `/security-review`.
6. PR uses `.github/pull_request_template.md`. Put T-xx in the commit and PR title.
7. A decision made or changed updates `docs/decisions.md` in the same PR.
8. If you make a mistake a rule would have prevented, propose the rule for this file.
